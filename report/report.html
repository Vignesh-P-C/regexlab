ABSTRACT

Regular expressions are usually presented to students as an opaque, black-box feature of a programming language's standard library, which hides exactly the constructions – Thompson's construction, subset construction, and DFA minimization – that a compiler-design course asks students to learn. RegexLab is a teaching tool that removes that opacity: it is a hand-built, dependency-free regular-expression engine that compiles a supported pattern through an explicit, inspectable pass pipeline – parser, Thompson's construction, subset construction, Moore's minimization, and a matcher – and exposes every intermediate structure (the abstract syntax tree, the nondeterministic finite automaton, the deterministic finite automaton, and the minimized deterministic finite automaton) to a learner, rather than only a final match/no-match verdict.

The engine is implemented twice, independently, as a deliberate correctness strategy: once in TypeScript, kept as the original design-validation prototype, and once in C++20 compiled to WebAssembly, which is the production engine actually shipped to the browser. Both implementations are validated by differential testing against two independent, battle-tested reference engines – native C++ std::regex and JavaScript's native RegExp – over thousands of randomly generated patterns and inputs, so that a correctness bug would have to reproduce independently in two languages and two test frameworks to go unnoticed. On top of the core pipeline, the project adds a Subset Growth / NFA Structure Lab, which exposes structural automaton measurements (raw, reachable, and minimized state counts; the theoretical powerset ceiling), and a Bounded Optimization Explorer, which deterministically searches a strictly bounded space of epsilon-edge-deletion candidates on the Thompson NFA, checks each candidate for language equivalence against the baseline using a product-construction equivalence procedure, and reports a verified Pareto frontier of safe, size-reducing candidates – reporting a shortest distinguishing witness for every unsafe candidate, and "inconclusive" rather than a guess when a resource limit is hit first.

This report documents the system's architecture, its explicit mapping onto the compiler-design syllabus (lexical analysis via the indirect regex-to-DFA route; syntax analysis via hand-written recursive-descent parsing; code generation via the matcher and the WebAssembly compilation step; DFA minimization as the project's stand-in for the optimization phase), its resource-safety guards (bounded pattern length, nesting depth, NFA state count, and minimization work), its automated test results (209 passing Vitest cases across 20 files; 81 passing native C++ Catch2 test cases totalling 4,923 assertions), and a specific regression this report's authors found and fixed during review – a minimization-pass performance regression that had silently dropped an alphabet-compression optimization, causing one previously legal pattern to be wrongly rejected as too complex – together with the verified timing evidence for the fix. The system's limitations are stated plainly: only the indirect route to a DFA is implemented, not the direct method; only Moore's minimization is implemented, not Hopcroft's; matching is full-string only; the alphabet is ASCII only; and the optimizer finds a verified-safe reduction within its search bound, not a provably minimum NFA.

CHAPTER 1
INTRODUCTION

1.1 Background

A regular expression engine is one of the most common pieces of compiler technology that a working programmer uses without ever seeing its internals. Yet the construction a regular-expression-to-DFA compiler performs is exactly the worked example used to introduce lexical analysis in the course's prescribed textbook, Aho, Lam, Sethi and Ullman's Compilers: Principles, Techniques, and Tools (2nd ed.): a regular expression becomes a syntax tree, the syntax tree becomes a nondeterministic finite automaton (NFA) by Thompson's construction, the NFA becomes a deterministic finite automaton (DFA) by subset construction (independently described by Rabin and Scott), and the DFA can be reduced to a unique minimal DFA by a state-equivalence algorithm such as Moore's or Hopcroft's. RegexLab builds exactly this pipeline, by hand, with no regular-expression library and no automata-theory package, and makes every intermediate structure visible to a learner.

1.2 Motivations

Three motivations shaped the project. First, a pedagogical one: automata theory is usually taught on paper, with students drawing NFAs and DFAs by hand for small examples; a tool that performs the same constructions on arbitrary (bounded) input and lets a learner step through them turns a static diagram into an interactive artifact. Second, a correctness motivation: because the same algorithms are re-implemented in two different languages (TypeScript and C++) and cross-checked against two independent reference engines, the project is a genuine exercise in differential testing, not only in parsing. Third, a resume/portfolio motivation, stated honestly: the project maps cleanly onto named, citable constructions from the compiler-design syllabus, and the WebAssembly compilation step is itself a second, literal code-generation stage, giving the project's claims – "implemented Thompson's construction, subset construction, and Moore's minimization from scratch" – a concrete, verifiable basis in the code rather than being a vague description.

1.3 Scope

In scope: a hand-written recursive-descent parser for an extended regular-expression grammar (literal characters with backslash-escaping, concatenation, alternation, Kleene star, one-or-more, zero-or-one, parenthesised grouping, character classes, the wildcard ., and the shorthand classes \d, \w, \s and their negations); Thompson's construction; subset construction; Moore's DFA minimization; a DFA-driven matcher; a hand-rolled SVG automaton visualizer with step-by-step playback; a Subset Growth / NFA Structure Lab exposing structural automaton measurements; and a Bounded Optimization Explorer that searches a strictly bounded space of epsilon-edge deletions and verifies each candidate's language equivalence.

Out of scope, by an explicit, theory-grounded decision rather than an oversight: the direct DFA-construction method (nullable/firstpos/lastpos/followpos); Hopcroft's faster minimization algorithm; substring/partial matching; backreferences and lookahead/lookbehind (both of which break the regular-language guarantee); and any claim that the bounded optimizer finds a provably minimum-size NFA, as opposed to a verified-safe reduction within its configured search bound.

CHAPTER 2
PROJECT DESCRIPTION AND GOALS

2.1 Literature Review

The theoretical foundation of this project rests on a small number of classical results. Kleene's characterization of regular languages is realised constructively by Thompson's construction [1], which builds an NFA from a regular expression in time linear in the expression's size, using a small number of fixed per-operator wiring rules. Rabin and Scott [2] gave the subset-construction (powerset) algorithm that determinizes any NFA into an equivalent DFA, at the cost of a worst-case exponential blow-up in state count that this report states honestly rather than hides. Moore [3] gave an iterative partition-refinement algorithm for collapsing a DFA to its unique minimal equivalent, later improved asymptotically by Hopcroft [4] from O(n²·k) to O(n·log n·k) by always refining using the smaller half of a split. Aho, Lam, Sethi and Ullman [5] is the textbook that frames all of the above as the worked example for a course's lexical-analysis module, and is the explicit syllabus anchor for this project's design.

Outside the classical automata-theory line, Cox [6] documents, from an engineering perspective, why real-world regular-expression libraries that use backtracking search can exhibit exponential-time matching on adversarial input, and argues for automaton-based matching (as this project uses) as the principled alternative. More recent formal work continues to refine these constructions and their complexity: Baburin and Cotterell [7] study glushkov-style and related finite-automaton constructions for regular expressions; Jiang and Ravikumar [8] give complexity results for minimizing and transforming finite automata under various equivalence notions; and Holzer et al. [9] study the state complexity of operations on finite automata. These sources are cited to situate the project's algorithms in the literature, not to claim that RegexLab contributes a new result to that literature.

2.2 Research Gap

To our knowledge, not found in the sources reviewed: an openly built, dependency-free, dual-language (TypeScript and WebAssembly-compiled C++) regular-expression compiler pipeline that is explicitly instrumented for teaching – i.e. one that exposes every pass's intermediate output to an interactive visualizer, and that additionally includes a bounded, verified NFA-structure optimizer that reports a distinguishing witness string whenever it proves a simplification unsafe. Most teaching implementations of these algorithms that we are aware of exist as standalone scripts or notebook exercises producing a single final diagram, not as a tested, two-implementation, browser-deployed pipeline with an automated, bounded safety-verified optimization step.

2.3 Objectives

The project's objectives were: (1) implement Thompson's construction, subset construction, and Moore's minimization from scratch, with no automata or regex library, in two independent language implementations; (2) validate both implementations by differential testing against independent reference engines; (3) expose every pass's output through an interactive, hand-rolled SVG visualizer; (4) add a bounded, formally-verified NFA-structure exploration feature (the Bounded Optimization Explorer) that never reports a false "safe" simplification; (5) compile the production engine to WebAssembly and verify its resource guards directly in a real browser build; and (6) document the project's syllabus mapping, complexity analysis, and limitations honestly, including where the mapping is thin.

2.4 Problem Statement

Given a regular expression drawn from a supported extended grammar and a candidate input string, determine (a) whether the input belongs to the language described by the expression, using only hand-built automata-theoretic machinery, within explicit, enforced resource bounds on pattern length, nesting depth, NFA state count, and minimization work; and (b) whether a given bounded set of structural simplifications to the expression's Thompson NFA (specifically, epsilon-edge deletions) preserves the recognized language exactly, proving the answer by product-construction equivalence checking rather than by heuristic or sampling, and reporting a concrete shortest distinguishing input whenever the answer is "no".

2.5 Project Plan

The project was planned in phases, tracked against a living progress tracker in the project team's own internal working-agreement document: a Core phase (literal characters, concatenation, alternation, Kleene star, grouping, the full five-pass pipeline in both languages, golden-value and differential tests, the WebAssembly binding, the visualizer, and Moore's minimization); Stretch A (the + and ? quantifiers); Stretch B ([a–z]-style character classes); and an explicitly locked-out Hard Stretch tier (Hopcroft's minimization, isomorphism-based equivalence testing) that the team deliberately did not start, since it was gated behind both teammates being able to explain the simpler Moore's-algorithm version unaided first. The Subset Growth / NFA Structure Lab and the Bounded Optimization Explorer were planned and built as a later, explicitly scoped addition on top of a already-working Core.

3.2 Feasibility Study

Technical feasibility: every algorithm used (Thompson's construction, subset construction, Moore's minimization, product-construction equivalence checking) is a well-documented, textbook-level algorithm with no open research risk; the main technical risk, confirmed and mitigated during the project, was unbounded recursion/state growth on adversarial input, addressed with explicit pattern-length, nesting-depth, NFA-state, and minimization-work guards.

Economic feasibility: the entire toolchain – GCC/Clang, CMake, Node.js, TypeScript, Vitest, Catch2, Emscripten, React, and Vite – is free and open-source; the project incurs no licensing cost (see Table 7.4).

Social feasibility: the project is a self-contained teaching tool with no personal-data collection, no third-party tracking, and no dependence on a paid external service for its core engine; the only optional external dependency is an AI-assisted suggestion layer (planned, not required for the core pipeline to function), which is explicitly gated behind re-validation through the same hand-built parser before any suggestion is shown to a user.

Testing strategy

Testing proceeds in layers: (1) golden-value unit tests per pass, in both languages, ported 1:1; (2) a pipeline-equivalence test confirming the chained pipeline matches manually chaining the five passes; (3) differential testing – C++ against std::regex, TypeScript against native, anchored RegExp – over thousands of randomly generated (pattern, input) pairs; (4) strict compiler warnings (-Wall -Wextra); (5) mutation discipline (deliberately breaking the implementation to confirm a test goes red, then reverting); and (6) resource-guard tests that deliberately configure a tiny budget to confirm each guard actually fires.

CHAPTER 6
PROJECT DEMONSTRATION

A typical demonstration walkthrough proceeds as follows. A learner enters a pattern, for example (a|b)*abb, and a test string, for example ababb. The engine parses the pattern into an AST, builds the 14-state Thompson NFA, determinizes it by subset construction into a 5-state DFA, minimizes it by Moore's algorithm into a 4-state minimal DFA, and matches the test string, producing a step-by-step trace that accepts the string (verified facts: see Table 7.1). The visualizer renders each of the AST, NFA, DFA, and minimized DFA as an SVG graph, with playback controls that highlight the currently active state(s) as each input character is consumed; if a character has no outgoing transition in the DFA or minimized DFA view, the visualizer renders an explicit rejecting sink state and highlights the failing character, while the NFA view is deliberately left without a fabricated sink (a true NFA has partial transitions by nature).

A second walkthrough demonstrates the Subset Growth / NFA Structure Lab: for the same or a different pattern, the panel reports the raw NFA state count, the number of states subset construction actually reaches (as opposed to the theoretical 2|Q| powerset ceiling), and the minimized DFA's state count, letting a learner directly compare the theoretical worst case against what is actually reached.

A third walkthrough demonstrates the Bounded Optimization Explorer: given an NFA, the explorer enumerates candidate epsilon-edge deletions up to a configured edit depth, checks each candidate's language equivalence against the baseline NFA using a product-construction procedure, and reports every candidate as either "equivalent" (safe to apply, on the verified Pareto frontier if it is also non-dominated on size) or "different" together with a concrete shortest distinguishing input string that the baseline accepts and the candidate rejects (or vice versa) – see Table 7.3 for two such verified examples, one of each kind, computed directly by the engine for this report.

Note: live browser screenshots of this walkthrough were not captured in this report-writing session, for the reason stated in the List of Figures; the counts and examples quoted above were produced directly by running the compiled native engine library against the exact patterns shown, not estimated or recalled.

7.2 A regression found and fixed during this review, with timing evidence

While preparing this report, the authors reviewed the state of pull request #72 and found that its minimization pass had silently dropped an alphabet equivalence-class compression optimization that exists on the project's main branch (added for a prior issue, #64), and had replaced the original state²×alphabet work-budget check with a flat 5,000,000-unit budget measured against the uncompressed alphabet. The practical effect: a legal, previously-accepted pattern (five hundred repetitions of the wildcard ., at the 500-character length cap) was wrongly rejected as AutomatonTooComplexError, because the wildcard's 126-symbol alphabet, left uncompressed, pushed the work estimate over budget even though the compressed alphabet for that exact pattern is a single equivalence class. The fix, applied and verified in this session, restores the compression step (grouping alphabet symbols into equivalence classes by identical transition behaviour before computing the refinement work estimate) in both the TypeScript and the C++ minimization passes, while keeping the pull request's own added capability – an explicit, configurable MinimizationLimits parameter and a shared AutomatonTooComplexError type.

7.3 Bounded-optimizer safe and unsafe deletion examples

Table 7.3 – Bounded-optimizer safe vs. unsafe epsilon-deletion examples (computed directly by the engine, this session)
PatternCandidate editEquivalence resultWitness
a|aDelete one of the two branch-entry epsilon edges (delete-eps:1>5)Equivalent (safe)— (no distinguishing input exists; the other branch still reaches accept on a)

The safe example illustrates a genuinely redundant structure: Thompson's construction for a|a builds two parallel branches that both recognize the literal string a; deleting either branch's own entry edge into the shared accept state leaves the other branch intact, so the language is unchanged. The unsafe example illustrates why the explorer must verify every candidate rather than apply a syntactic heuristic: the deleted edge looks structurally similar to a redundant one, but it is on the only path into the mandatory trailing a, so deleting it removes acceptance of every string that needs that a, and the explorer's product-construction equivalence check finds and reports the shortest such string, "ab", rather than merely saying "unsafe".

7.4 Discrepancies against the project's own report-data file

The project repository's own data_for_report.md (dated 25 October 2026) was checked against this report's independently re-derived numbers. The automated test counts (209 Vitest tests / 20 files; 81 Catch2 cases / 4,923 assertions) and the bounded-search default limits (12 eligible edges, edit depth 2, 24 candidates, 128 DFA states, 100,000 work units, 10,000 product-state pairs) matched exactly. The compiled-WASM probe count in that file (27/27) was not independently re-verified in this session, because this report's authors restored four previously-deleted timed probes to scripts/check-wasm-limits.mjs as part of the §7.2 fix, and did not rebuild the WASM target in the available time – so the true current probe count after that restoration (27 existing + 4 restored = 31, if the rest of the file is unchanged) is stated here as a predicted, not measured, number, and is flagged as such rather than claimed as verified.

CHAPTER 8
CONCLUSION AND FUTURE WORK

RegexLab demonstrates that the classical automata-theory pipeline named in a compiler-design syllabus – Thompson's construction, subset construction, and DFA minimization – can be built by hand, in two independent language implementations, validated by differential testing against industrial-strength reference engines, and shipped as an interactive, browser-based teaching tool, including a bounded, formally-verified NFA-structure optimizer that never reports a false safety claim. The project is explicit about where its syllabus coverage is deep (lexical analysis, via the indirect route) and where it is necessarily thin (semantic analysis, parallelism), rather than overstating its scope.

This report's own review process also found and fixed a genuine regression – a lost alphabet-compression optimization in the minimization pass that caused a previously-legal pattern to be wrongly rejected – which is itself evidence for the project's own stated correctness strategy: having two independently-maintained implementations and an explicit, checkable complexity derivation made the regression's root cause identifiable and fixable with verified timing evidence, rather than merely "fixed and hoped".

Future work, scoped but deliberately not started in this phase, includes: implementing Hopcroft's O(n·log n·k) minimization alongside Moore's, with a test asserting both produce the same minimized automaton; implementing the direct DFA-construction method (nullable/firstpos/lastpos/followpos) as a second, independently-verifiable route to the same DFA; adding an explicit DFA-state-count guard to subset construction (currently unguarded, relying only on the indirect bound from the pattern-length cap); and completing the planned AI-assisted suggestion layer, whose single hard architectural rule – that any AI-proposed fix must be re-validated by the same hand-built parser before ever being shown to a user – is already decided and documented, even though the feature itself is not yet built.

The restored alphabet equivalence-class compression step in MinimizationPass (TypeScript), central to the fix described in §7.2:

function representativeAlphabetOf(dfa: Automaton, alphabet: string[], stateCount: number): string[] {
  const seenKeys = new Set<string>();
  const representatives: string[] = [];
  for (const symbol of alphabet) {
    const column: string[] = [];
    for (let state = 0; state < stateCount; state++) {
      const dest = dfa.transitions.get(state)?.get(symbol)?.[0];
      column.push(dest === undefined ? "-" : String(dest));
    }
    const key = column.join(",");
    if (!seenKeys.has(key)) { seenKeys.add(key); representatives.push(symbol); }
  }
  return representatives;
}
