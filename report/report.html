ABSTRACT

Most programmers use a regular expression every week and never see what actually happens underneath it. That gap is exactly what RegexLab sets out to close. It is a hand-built, dependency-free regular expression engine that compiles a pattern through a visible, step-by-step pipeline rather than hiding everything behind a single match or no-match answer. A pattern is parsed into an abstract syntax tree, turned into a nondeterministic finite automaton by Thompson's construction, determinized into a DFA by subset construction, and reduced to its unique minimal form by Moore's algorithm, and every one of those intermediate structures is kept around and shown to the learner, not discarded once the final answer is ready.

We built the engine twice on purpose. A TypeScript version came first and still lives in the repository as the design-validation prototype, while the production engine is written in C++20 and compiled to WebAssembly so it runs directly in the browser. Both versions are checked against two independent, well-trusted reference engines, native C++'s std::regex and JavaScript's built-in RegExp, across thousands of randomly generated patterns and inputs. A real bug would have to slip past both languages and both test frameworks at once to go unnoticed, which is a much stronger bar than trusting either engine alone. On top of that core pipeline we added two features that go beyond the standard construction: a Subset Growth / NFA Structure Lab that reports raw, reachable, and minimized state counts alongside the theoretical powerset ceiling, and a Bounded Optimization Explorer that searches a strictly bounded space of epsilon-edge deletions on the Thompson NFA and proves, by product-construction equivalence checking, which ones are safe. Every candidate it cannot prove safe comes with a concrete witness string showing exactly where the language changed, and when a configured resource limit is hit before a proof completes, it says "inconclusive" instead of guessing.

This report walks through the system's architecture, maps it onto the compiler-design syllabus (lexical analysis through the indirect regex-to-DFA route, syntax analysis through a hand-written recursive-descent parser, code generation through the matcher and the WebAssembly build, DFA minimization standing in for the optimization phase), and lays out its resource-safety guards on pattern length, nesting depth, NFA state count, and minimization work. It documents the automated test results, 209 Vitest cases across 20 files and 81 native C++ Catch2 cases totalling 4,923 assertions, all passing, and a real regression we found and fixed while reviewing the project's own pull request history: a minimization-pass bug that had quietly dropped an alphabet-compression optimization and wrongly rejected a perfectly legal pattern as too complex, along with the timing evidence confirming the fix. We are just as upfront about what the project does not do. Only the indirect route to a DFA is implemented, not the direct method. Only Moore's minimization is implemented, not Hopcroft's. Matching is full-string only, the alphabet is ASCII only, and the bounded optimizer gives a verified-safe reduction within its search bound, not a provably minimum-size NFA.

CHAPTER 1
INTRODUCTION

1.1 Background

A regular expression engine is one of the most heavily used pieces of compiler technology that a working programmer never actually sees the inside of. It is also, conveniently, the worked example that the course's prescribed textbook uses to introduce lexical analysis: Aho, Lam, Sethi and Ullman's Compilers: Principles, Techniques, and Tools (2nd ed.) walks through turning a regular expression into a syntax tree, the syntax tree into a nondeterministic finite automaton (NFA) by Thompson's construction, the NFA into a deterministic finite automaton (DFA) by subset construction (independently described by Rabin and Scott), and finally reducing that DFA to its unique minimal form by a state-equivalence algorithm such as Moore's or Hopcroft's. RegexLab builds exactly this pipeline by hand, with no regular-expression library and no automata-theory package anywhere in the engine, and keeps every intermediate structure visible to whoever is using it.

1.2 Motivations

Three things pulled us toward this project. The first was simply wanting to see automata theory move: it is normally taught on paper, with small NFAs and DFAs drawn by hand, and we wanted a tool that performs the same constructions on real input and lets a learner step through them the way a debugger steps through code. The second was correctness as a discipline in its own right. Building the same algorithms twice, once in TypeScript and once in C++, and checking both against independent reference engines turned the project into a genuine exercise in differential testing, not just parsing. The third, said plainly, was that this project gave us something concrete to point to. "Implemented Thompson's construction, subset construction, and Moore's minimization from scratch" is a claim we can actually back up line by line in the code, and the WebAssembly compilation step is a second, literal code-generation stage on top of the first.

1.3 Scope

In scope: a hand-written recursive-descent parser for an extended regular-expression grammar, covering literal characters with backslash escaping, concatenation, alternation, the Kleene star, one-or-more and zero-or-one quantifiers, parenthesised grouping, character classes, the wildcard ., and the shorthand classes \d, \w, \s and their negations. Also in scope: Thompson's construction, subset construction, Moore's DFA minimization, a DFA-driven matcher, a hand-rolled SVG automaton visualizer with step-by-step playback, a Subset Growth / NFA Structure Lab that exposes structural automaton measurements, and a Bounded Optimization Explorer that searches a strictly bounded space of epsilon-edge deletions and verifies every candidate's language equivalence.

Out of scope, and left out on purpose rather than forgotten: the direct DFA-construction method (nullable, firstpos, lastpos, followpos), Hopcroft's faster minimization algorithm, substring or partial matching, and backreferences or lookahead/lookbehind, since both of the last two break the regular-language guarantee the whole project rests on. We have also been careful never to describe the bounded optimizer as finding a provably minimum-size NFA. What it finds is a verified-safe reduction within its configured search bound, and that distinction matters.

CHAPTER 2
PROJECT DESCRIPTION AND GOALS

2.1 Literature Review

This project rests on a handful of classical results. Kleene's characterization of regular languages is made constructive by Thompson's construction [1], which builds an NFA from a regular expression in time linear in the expression's size using a small set of fixed per-operator wiring rules. Rabin and Scott [2] gave the subset-construction algorithm that determinizes any NFA into an equivalent DFA, at the cost of a worst-case exponential blow-up in state count. We say that plainly in this report rather than quietly stepping around it. Moore [3] gave an iterative partition-refinement algorithm for collapsing a DFA to its unique minimal form, and Hopcroft [4] later improved on it asymptotically, O(n·log n·k) instead of Moore's O(n²·k), by always refining from the smaller half of a split. That last sentence is a fact about the literature, not a claim about this project: RegexLab implements Moore's algorithm only (see §5.2 and §8), and Hopcroft's was deliberately left out. Aho, Lam, Sethi and Ullman [5] is the textbook that frames all of this as the worked example for a course's lexical-analysis module, and it is the explicit syllabus anchor behind this project's design.

Outside the purely theoretical line, Cox [6] explains from an engineering angle why real-world regex libraries built on backtracking search can blow up to exponential time on adversarial input, and makes the case for automaton-based matching, the approach this project takes, as the principled way around that problem. More recent work keeps pushing on how hard these constructions really are. Baburin and Cotterell [7] show that estimating how much subset construction's exponential blow-up will actually cost is itself PSPACE-hard, which is a sharper and more recent version of exactly the honesty this report tries to practise around §2.1's own exponential-blow-up admission. Jiang and Ravikumar [8] prove that finding a minimum-size NFA for a given regular language is PSPACE-complete, and Clemente and Mayr [9] give practical algorithms for reducing an NFA's size while provably preserving its language, which is the same safety guarantee the Bounded Optimization Explorer (§2.3, §7.3) is built around, just at a scale this project's bounded search does not attempt. These sources place the project's algorithms in context; we are not claiming RegexLab contributes a new result to that literature.

2.2 Research Gap

To our knowledge, and we have looked, we have not found an openly built, dependency-free, two-language regular-expression compiler pipeline that is built specifically for teaching in the way RegexLab is: one that exposes every pass's intermediate output to an interactive visualizer and also includes a bounded, verified NFA-structure optimizer that hands back a concrete counterexample whenever it proves a simplification unsafe. Most teaching implementations of these algorithms that we came across are standalone scripts or notebook exercises that produce one final diagram and stop there, not a tested, dual-implementation, browser-deployed pipeline with an automated and safety-verified optimization step built in.

2.3 Objectives

We set out with six concrete goals. Implement Thompson's construction, subset construction, and Moore's minimization from scratch, with no automata or regex library, in two independent language implementations. Validate both implementations by differential testing against independent reference engines. Expose every pass's output through an interactive, hand-rolled SVG visualizer. Add a bounded, formally-verified NFA-structure exploration feature, the Bounded Optimization Explorer, that never reports a false "safe" simplification. Compile the production engine to WebAssembly and verify its resource guards directly in a real browser build. And document the project's syllabus mapping, complexity analysis, and limitations honestly, including the parts where the mapping is thin.

2.4 Problem Statement

Given a regular expression from the supported extended grammar and a candidate input string, the engine has two jobs. First, decide whether the input belongs to the language the expression describes, using only hand-built automata-theoretic machinery and within explicit, enforced bounds on pattern length, nesting depth, NFA state count, and minimization work. Second, given a bounded set of structural simplifications to the expression's Thompson NFA (specifically, epsilon-edge deletions), decide whether each one preserves the recognized language exactly. That second answer has to come from product-construction equivalence checking, not from a heuristic or from sampling, and whenever the answer is no, the engine has to produce a concrete, shortest distinguishing input.

2.5 Project Plan

We planned the project in phases and tracked progress against a living checklist in our own internal working-agreement document. The Core phase covered literal characters, concatenation, alternation, the Kleene star, grouping, the full five-pass pipeline in both languages, golden-value and differential tests, the WebAssembly binding, the visualizer, and Moore's minimization. Stretch A added the + and ? quantifiers, and Stretch B added [a–z]-style character classes. A Hard Stretch tier, Hopcroft's minimization and isomorphism-based equivalence testing, was explicitly locked and never started, since we had agreed it would only be worth attempting once both of us could explain the simpler Moore's-algorithm version from memory, unaided. The Subset Growth / NFA Structure Lab and the Bounded Optimization Explorer came later, as a deliberately scoped addition once the Core was already working end to end.

3.2 Feasibility Study

Technical feasibility: every algorithm we used (Thompson's construction, subset construction, Moore's minimization, product-construction equivalence checking) is well-documented and textbook-level, so there was no open research risk. The one real technical risk we ran into was unbounded recursion and state growth on adversarial input, and we closed it with explicit guards on pattern length, nesting depth, NFA state count, and minimization work.

Economic feasibility: the whole toolchain is free and open source: GCC/Clang, CMake, Node.js, TypeScript, Vitest, Catch2, Emscripten, React, and Vite. The project carries no licensing cost at all (see Table 7.4).

Social feasibility: this is a self-contained teaching tool. It collects no personal data, tracks nothing, and does not depend on any paid external service for its core engine. The only optional piece that would reach outside the browser is an AI-assisted suggestion layer, which is still only planned and not required for the core pipeline to work, and even that is designed so any suggestion it makes has to pass back through the same hand-built parser before a user ever sees it.

5.3 Testing strategy

Testing happens in layers. Golden-value unit tests cover each pass individually, ported one-to-one between the two languages. A pipeline-equivalence test confirms that calling the chained pipeline gives the same result as manually chaining the five passes yourself. Differential testing runs the C++ engine against std::regex and the TypeScript engine against native, anchored RegExp over thousands of randomly generated pattern-and-input pairs. The C++ build compiles with strict warnings (-Wall -Wextra) enabled. We also practise mutation discipline: deliberately break something, confirm the relevant test actually goes red, then revert it, so we know the tests are testing something real. And every resource guard has its own test that configures a deliberately tiny budget to confirm the guard actually fires rather than silently doing nothing.

CHAPTER 6
PROJECT DEMONSTRATION

A typical walkthrough starts with a learner typing in a pattern, say (a|b)*abb, and a test string, say ababb. The engine parses the pattern into an AST, builds the 14-state Thompson NFA, determinizes it into a 5-state DFA, minimizes that down to a 4-state DFA by Moore's algorithm, and runs the test string through it, producing a step-by-step trace that ends in acceptance (these exact numbers are verified in Table 7.1, not approximated). The visualizer draws the AST, NFA, DFA, and minimized DFA as SVG graphs with playback controls that light up the active state or states as each character is consumed. If a character has nowhere to go in the DFA or minimized DFA view, the visualizer shows an explicit rejecting sink state and highlights the character that failed. The NFA view is left without a fabricated sink on purpose, since a real NFA has partial transitions by nature and inventing a sink there would misrepresent it.

A second walkthrough shows the Subset Growth / NFA Structure Lab. For a given pattern, the panel reports the raw NFA state count, how many states subset construction actually reaches, and the minimized DFA's state count, side by side with the theoretical powerset ceiling of 2|Q|. Seeing the gap between that ceiling and what actually gets built is, in our experience, the moment this kind of theory stops being abstract.

A third walkthrough runs the Bounded Optimization Explorer. Given an NFA, it enumerates candidate epsilon-edge deletions up to a configured edit depth, checks each one against the baseline NFA for language equivalence using a product-construction procedure, and labels every candidate either equivalent, meaning it is safe to apply and lands on the verified Pareto frontier if it is also not dominated on size, or different, with a concrete shortest string that the baseline accepts and the candidate rejects (or the other way around). Table 7.3 shows one verified example of each kind, computed directly by the engine, not written up from memory.

7.2 A regression found and fixed during this review, with timing evidence

While reviewing pull request #72, we found that its minimization pass had quietly lost an alphabet equivalence-class compression optimization that already exists on the project's main branch, added earlier for issue #64. In its place sat a flat 5,000,000-unit work budget checked against the uncompressed alphabet instead of the compressed one. In practice this meant a perfectly legal pattern, five hundred repetitions of the wildcard . sitting right at the 500-character length cap, got wrongly rejected as AutomatonTooComplexError. The wildcard's alphabet has 126 symbols, and left uncompressed that pushed the work estimate over budget, even though every one of those 126 symbols collapses into a single equivalence class once you actually compress them. We restored the compression step, which groups alphabet symbols by identical transition behaviour before the work estimate is computed, in both the TypeScript and the C++ minimization passes, and kept everything the pull request itself had added: the configurable MinimizationLimits parameter and the shared AutomatonTooComplexError type.

The safe example is a genuinely redundant structure. Thompson's construction for a|a builds two parallel branches that both recognize the literal string a, so deleting either branch's own entry edge into the shared accept state leaves the other branch perfectly intact and the language unchanged. The unsafe example is why the explorer has to verify every candidate instead of trusting a syntactic heuristic. That edge looks structurally similar to the redundant kind, but it actually sits on the only path into the mandatory trailing a, so deleting it removes acceptance of every string that needs that a. The explorer's product-construction equivalence check catches this and reports the shortest such string, "ab", instead of simply saying "unsafe" and leaving the reader to take it on faith.

CHAPTER 8
CONCLUSION AND FUTURE WORK

When we started, "implement a regex engine" sounded like a weekend project. It was not, and that turned out to be the point. RegexLab shows that the classical automata-theory pipeline named in a compiler-design syllabus, Thompson's construction, subset construction, and DFA minimization, can genuinely be built by hand, in two independent languages, checked by differential testing against industrial-strength reference engines, and shipped as an interactive browser tool, with a bounded and formally verified NFA-structure optimizer on top that never makes a false safety claim. We have tried throughout this report to be honest about where the syllabus coverage runs deep, lexical analysis through the indirect route, and where it stays thin, semantic analysis and parallelism, rather than stretching the project to look broader than it is.

The part of this work we are proudest of is not a feature, it is a process. While reviewing our own pull request history for this report, we found a real regression: a lost alphabet-compression optimization in the minimization pass that was quietly rejecting a pattern it had no business rejecting. Finding it was not luck. It came directly from the correctness strategy the project is built on, two independently maintained implementations and a complexity derivation we could actually check by hand, and that same strategy is what let us fix it and prove the fix with real timing evidence instead of just patching the symptom and hoping. That is, honestly, the most reassuring thing about the whole project: when something did go wrong, the project's own design caught it.

There is plenty we would still like to build. Hopcroft's O(n·log n·k) minimization alongside Moore's, with a test proving both produce the same minimized automaton. The direct DFA-construction method, nullable/firstpos/lastpos/followpos, as a second and independently verifiable route to the same DFA. An explicit DFA-state-count guard on subset construction, which today relies only on the indirect bound the pattern-length cap happens to provide. And the AI-assisted suggestion layer itself, whose one non-negotiable rule, that any AI-proposed fix has to be re-validated by the same hand-built parser before a user ever sees it, is already decided and written down even though the feature isn't built yet. None of this was rushed, and we would rather hand in a smaller project we can defend completely than a longer feature list we cannot.

The extended grammar implemented by ParserPass is shown below. We verified it against the per-rule docblocks that actually sit above each parsing function in engine/passes/parser-pass.cpp (for example /** regex ::= term ('|' term)* */ above parseRegex(), and /** atom ::= ASCII_CHAR | '.' | '[' class ']' | '(' regex ')' | escape */ above parseAtom()), and separately against the grammar's own reference document, docs/regex-grammar-v1.md.

regex          ::= term ('|' term)*
term           ::= factor+
factor         ::= atom quantifier?
quantifier     ::= '*' | '+' | '?'
atom           ::= CHAR | '.' | characterClass | '(' regex ')'
characterClass ::= '[' '^'? classItem+ ']'
classItem      ::= classAtom ('-' classAtom)?
classAtom      ::= ASCII_LITERAL | ESCAPE | SHORTHAND   ( \d \w \s \D \W \S )

This is the full extended grammar from the issue #60/#64 follow-up, not the narrower Core-phase grammar (literal, concat, alt, star, parens only) that shipped first, as described in §2.5. + and ? are real postfix quantifiers that produce dedicated PlusNode/OptionalNode AST nodes, not literal characters, and ., character classes, and shorthand classes all desugar to a single CharacterSetNode Thompson fragment, which is what §5.2's complexity note on alphabet size is referring to.

The restored alphabet equivalence-class compression step in MinimizationPass (TypeScript), central to the fix described in §7.2, copied verbatim from engine/passes/minimization-pass.ts:

function representativeAlphabetOf(dfa: Automaton, alphabet: string[], stateCount: number): string[] {
  const classKeyOf = new Map<string, string>(); // symbol -> its class's key (the full transition column)
  const seenKeys = new Set<string>();
  const representatives: string[] = [];

  for (const symbol of alphabet) {
    const column: string[] = [];
    for (let state = 0; state < stateCount; state++) {
      const dest = dfa.transitions.get(state)?.get(symbol)?.[0];
      column.push(dest === undefined ? "-" : String(dest));
    }
    const key = column.join(",");
    classKeyOf.set(symbol, key);
    if (!seenKeys.has(key)) {
      seenKeys.add(key);
      representatives.push(symbol);
    }
  }

  return representatives;
}

The Thompson's-construction rule for alternation (TypeScript; C++ mirrors it exactly), copied verbatim from engine/passes/thompson-pass.ts:

case "alt": {
  const left = buildFragment(node.left, builder);
  const right = buildFragment(node.right, builder);
  const start = builder.newState();
  const accept = builder.newState();
  builder.addTransition(start, "eps", left.start);
  builder.addTransition(start, "eps", right.start);
  builder.addTransition(left.accept, "eps", accept);
  builder.addTransition(right.accept, "eps", accept);
  return { start, accept };
}
